## 0. 总体结论

### 0.1 一句话结论

这套构思在「**技术路线真实性**」上明显高于一般策划交付：ACP 官方通道用真实 turn 实测闭环、62492 明确判定不可依赖、Harness 能力边界（提交点粒度流式、无文件 API、暂停不支持、headless 无审批）全部如实标注、环境数据来自实测。**但它还不是可直接冻结进入开发的基线**：存在 **3 个 P0 契约级矛盾**（传输形态、验收范围、审批终态语义）与 **12 个 P1 需求/验收缺口**，其中相当一部分是「主方案摘要落后于设计分册」造成的——用户若只看主方案拍板，会批准一份与实现不一致的方案。

### 3.6 任务状态机与错误码（审批终态）

| 说法来源 | 原文 | 隐含终态 |
| --- | --- | --- |
| PROTOCOL §2.10 L826-827 | 「未确认超时（120 秒）→ 任务自动 failed，errorCode=70003」 | 超时 → failed |
| PROTOCOL §8.1 | 「超时一律按拒绝回 cancelled、绝不默认同意」 | 超时 → cancelled |
| PROTOCOL §8.3 ④ | 「拒绝→reject-once，工具不执行…任务通常 completed 非 failed」 | 拒绝 → completed |
| REMOTE_AGENT §5.1 | 「waiting_approval→failed：pre-flight 拒绝/审批超时/票据校验失败；in-flight 拒绝不降 failed」 | 超时 → failed（in-flight 拒绝 → running/completed） |
| REMOTE_AGENT §9 | 「审批超时→failed{reason:"approval_timeout"} 70003；审批拒绝→failed{reason:"approval_denied"} 70003」 | 拒绝 → failed |
| 策划案 7.3 / 2.3 | 高风险需确认；状态含"等待用户授权"；不得伪造 | 未规定终态语义（设计自由度） |

**结论**：同一动作（in-flight 审批被拒绝/超时）在 5 处有 4 种互斥描述；错误码 70003（DENIED）被超时复用而 70004（EXPIRED）闲置。这是 **P0-3**——M3 开工前必须产出一张"审批终态权威表"（建议：in-flight 拒绝→任务继续解释、最终 completed（hint: end_turn）；in-flight 超时→按拒绝处理、completed；pre-flight 拒绝/超时→failed，errorCode 分别 70003/70004；票据校验失败→failed 50002/70003 明确其一）。

## 4. 验收可测性逐条判定

**判定定义**：`可执行` = 已给出"操作 + 判定标准"，执行人照做即可判定；`部分可执行` = 有验证方向但缺命令/阈值/前置数据；`不可执行` = 当前方案下无法通过真实测试。**共同缺失**：18 项没有统一证据模板（每项应产出 `EVIDENCE-<编号>.md`：环境、命令、原始输出/截图/录屏、时间戳、执行人、结论），也没有"阈值表"（如实时性、首帧、恢复时间）。这直接关系到策划案第十章末句"不得仅页面展示/模拟数据/接口返回成功判定"的落实。

## 5. 遗漏与风险（策划案强调但构思未充分覆盖）

### 5.1 手机后台保活与推送（**高风险，M2/M3 关键路径**）

- 现状：MOBILE_UI §12 明确"后台不保持 WS，用推送唤醒"；§11 推送方案为 FCM+APNs，并承认"国内 Android 无 GMS 兜底未验证"（§15、MVP R6/A-03）。
- 问题：**审批通知与急停通知是产品安全链路的一环**。手机锁屏/后台被杀/无 GMS 时，`task.waiting_approval` 的 120 秒倒计时仍在跑 → 用户看到"任务已超时未执行"，产品体验等同"任务卡死"；急停只能依赖用户主动打开 App。
- 建议：M3 前做一次推送可行性决策（三选一）：
  1. Android 前台服务 + 本地通知（可保活 WS，代价是常驻通知）；2. 国内厂商推送通道（小米/华为/OPPO/vivo，接入成本 3–5 人日）；3. 接受"无推送"，但必须：审批有效期延长（如 10–30 分钟或不过期，与策划案"等待授权"状态语义一致）、UI 明确"打开 App 才能收到通知"、任务中心置顶待审批。
- 该项在 MVP §12 风险表未单列"推送不可用导致审批超时"的业务后果，建议补 R16。

### 5.2 Agent 开机自启的默认值（**合规风险**，对应 F-02 / P1-7）

- 策划案 3.1 明确"开机启动必须用户主动配置，不得默认静默启用"；REMOTE_AGENT ADR-AGENT-009 写"登录自启"+`autostart.ts` 注册表 Run；主方案写"默认关闭、用户勾选"，**分册未同步**。
- 建议：ADR-AGENT-009 增加一句"**安装程序与首次运行不得自动注册自启项；autostart 仅由用户在本地 UI 显式勾选后写入，默认关闭；卸载时清理**"，并把该项加入 M5 验收（安装包验收清单）。

### 5.3 Harness 审批阻塞导致任务"看起来卡死"（**高风险**，P1-6）

- 现状：in-flight 审批时 `session/prompt` 被阻塞、**占用并发槽**（REMOTE_AGENT §5.1/§5.2），全局并发仅 2。
- 问题：① 两个任务同时等待审批 → 新任务排队 30 分钟后 `queue_timeout` 失败；② 审批 120s 超时 + 无推送 = 用户回来发现失败；③ 策划案 2.3 有"等待用户授权"状态，语义上允许等待，与 120s 短超时冲突。
- 建议：① 审批等待中的任务**不占普通并发槽**（或为其单独设 2 个配额）；② 审批有效期从 120s 放宽到 10 分钟（安全与可用性的平衡；票据仍一次性），把"超时失败"改为"超时后任务回到 waiting_approval 并提示，不自动失败"（更符合策划案状态语义）；③ 与 P0-3 一起定终态。

### 5.4 多设备并发语义（**中等风险**，P2-18）

- 现状：PROTOCOL 支持一个账号多设备（`sys.auth.resume.devices[]`、每设备 seq）；MVP M5 才测"2 台"；主方案 R9 缓解写"单活动会话/设备 + 任务上限"；策划案 2.6"设备管理"、2.4"当前连接设备"暗示多设备。
- 问题：v1 是否允许多台电脑同时在线/同时执行任务？"单活动会话/设备"与"多设备列表/切换"语义冲突，且影响通知路由与并发配额。
- 建议：在 §7 决策点补一条"多设备支持范围"：推荐 v1 = 账号可绑多台设备、**同时只有 1 台处于"活动会话"**（其余可查看状态但不能并发执行），并把该约束写入 PROTOCOL（device_sessions 或 devices.active 字段）与 MOBILE_UI（非活动设备置灰）。

### 5.5 Telegram 式离线消息（**已覆盖，需澄清边界**）

- 现状：PROTOCOL §5.3 用 `device_events + seq + sys.resume/replay` 实现"手机断线重连补偿"，手机端 drift 缓存游标；MOBILE_UI §9 明确离线只读、仅发任务入队（但离线发任务与后端策略冲突，见 P1-2）。
- 判断：**离线消息的核心需求（不丢消息、打开即追赶）已覆盖**，且带 `replay.gap→REST 全量刷新` 兜底，设计优于策划案要求。边界需写清："App 被杀且无推送期间不产生实时提醒"（与策划案无冲突，但用户预期需明示）。

### 5.6 日志脱敏具体规则（**部分覆盖**）

- Agent 侧：REMOTE_AGENT §7.6 表格具体（token/secret 整值打码、prompt 只记长度+哈希、文件内容不落、路径保留盘符+末两级、IP 保留前三段、命令行密钥打码）——**完整**。
- 云端侧：仅约束 API `message` 字段不得含堆栈/SQL/令牌/绝对路径（PROTOCOL §1.3）与 audit_logs 路径哈希；**缺服务端应用日志（logback/JSON 日志）脱敏规范、审计日志保留期的访问控制、日志外发/备份策略**。
- 建议：补一页《云端日志与审计数据规范》，并在 `/api/health` 或自检脚本中加入"日志抽样不含明文 token/绝对路径"检查项。

### 5.7 "真实执行不得用模拟数据"的落实方式（P1-12）

- 现状：MVP ADR-ROAD-006 区分 Mock（仅链路）与真实验收；M0 §3.4 明确 Mock；主方案验收要求真实记录。**原则正确**，但缺工程手段：
  1. 无统一证据模板（见 §4 开头）；
  2. 无"Mock 开关"的强制约束（如 `DEV_MOCK=1` 仅 debug build 可开，release 构建禁止）；
  3. CI 在中无 DSH/无真机环境下如何运行：建议 ACP 契约测试（真 Harness）作为"夜间/本地"流水线，CI 跑 Mock+契约快照，并在验收报告标注"真实环境证据"；
  4. 无验收执行前"环境声明"（Flutter/PG/云/签名就绪后才有资格执行对应项，否则记录"未执行"而非"通过"）。
