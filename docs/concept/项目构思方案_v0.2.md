## 0. 一页纸结论（结论先行）

**这个项目可行，而且接入 Harness 的「钥匙」已经找到了——比策划案预期的风险低得多。**

实测发现四件事（全部本机实测，证据与原始日志见 `docs/research/`），直接改变了项目的技术路线判断：

| # | 实测发现 | 证据 | 对项目的意义 |
|---|---|---|---|
| 1 | **官方 ACP 通道可用（关键发现）**：`dsh --profile acp` 以 NDJSON JSON-RPC 2.0 over stdio 提供完整 ACP（Agent Client Protocol）服务端；对话、步骤级流式事件、工具调用（含完整命令）、取消、**审批**（`session/request_permission`）、多轮续跑、跨进程 `session/resume`、模型/推理强度切换，经约 25 次真实 turn **全部实测闭环** | `docs/research/HARNESS_INTERFACES.md` + `tools/harness_probe/probe_acp*.mjs` 与 `evidence/*.log.json` | **接入方式就此定案**：Remote Agent 以子进程驱动官方 ACP 服务端（官方 shipped profile、npm 公开包、MIT、`protocolVersion=1`）。不需要官方 Remote API、不需要逆向、不需要桌面自动化——策划案 3.2 的"官方接口"路线已经完全落地 |
| 2 | **没有面向外部程序的 HTTP Remote API**：`127.0.0.1:62492` 的 `/api` 是官方 Web 前端内部 RPC（launch-token→cookie、Host 栅栏、仅 loopback、端口随机、无文档） | 源码 `dsh-client-connection/lib/index.js`（1072 行）+ 实测 401→`/?token`→303+cookie | 手机/公网**不可能**也**不应该**直连 Harness；必须由同机 Remote Agent 出站连云端 → 印证策划案 4.2 架构，且天然安全 |
| 3 | **`dsh headless` 存在但有硬限制**：`--json` 输出固定 NDJSON 事件（session/status/tool_call/tool_result/final），**无审批通道、无取消**（审批需求时报 `requires approval, but no approval channel is available`），事件为提交点粒度 | `dsh headless --help` + 实测 36 条事件 | headless 只适合一次性批任务；**"等待授权/取消/续跑"的交互式主链路必须走 ACP** |
| 4 | 环境基本齐备：JDK 21 Temurin + Gradle 8.14、Android SDK + 模拟器（WHPX 加速）、Node 24、MSBuild + NSIS、ffmpeg gdigrab 抓屏实测通；**唯一硬缺口是 Flutter SDK（1.81GB，可下载）**，另有环境变量为空、PostgreSQL 未装 | `docs/research/ENVIRONMENT_REPORT.md`（428 行实机扫描 + 原始输出） | 阶段 2/3 可立即开工；Flutter/PG 约 0.5–1 天安装时间，需用户授权 |

**三个核心判断**

1. **项目本质不是"再做一个 AI 助手"，而是"给电脑上的 AI 程序员装一个手机遥控器"。**
   AI 能力已经由 Harness 提供，本项目 80% 的工作量在**通道、状态、安全、体验**，不在模型。任何"重写 Agent"的倾向都是资源浪费。

2. **真正的难点排序（与直觉不同）：**
   ① 手机端弱网/锁屏/切后台下的**可靠事件回放**（不是实时流，而是"可追赶的日志"）；
   ② **权限与紧急停止**的安全模型（远程控制自己电脑 = 把家门钥匙放云端）；
   ③ Harness **能力边界的诚实映射**（流式、审批、暂停、取消，不支持的必须显式降级）；
   ④ 远程桌面（技术最重、优先级最低，最后做）。

3. **最大风险已经从"能否接上 Harness"变成"如何把 ACP 事件做成可靠的手机体验"。**
   M0 不再是"证明可行"（本次调研已用真实 turn 实测完成），而是"工程化封装"（3 人日：契约测试 + E2E 冒烟）：把 ACP 客户端、能力探测封成 `HarnessAdapter`，产出 `docs/research/M0_FEASIBILITY.md`。剩余技术不确定性只有一条：**ACP 仍是 rc（0.2.1-rc.5）且无随包文档**，对策 = 锁版本 + 忽略未知事件类型 + JSON-RPC 错误统一映射 + 升级跑回归探测。

**与策划案的 3 处调整建议（需用户同意）**

| # | 策划案原安排 | 建议调整 | 理由 |
|---|---|---|---|
| A1 | 第三阶段才做「Harness 检测与适配」 | 已提前完成（本次调研即 M0 主体，实测结论见第 3 章） | 唯一能推翻方案的技术风险已消除；剩下的是工程化封装（3 人日） |
| A2 | 固定"手机→Java 云端→电脑 Agent"单一路径 | **通信形态不增加直连**（手机永不直连电脑、Agent 永远出站，三条边界不变）；只增加**部署形态**选项：开发/试用期把 Java 后端跑在自己 PC/NAS 上，用 Tailscale/WireGuard 组网让手机访问这个"云端"，上线再迁公有云 | 让产品验证不被"买服务器、备案域名、签证书"阻塞，又不破坏安全边界（审核 P0-1 的收敛方案） |
| A3 | 第六阶段统一做远程桌面 | 拆成三级（L1 看一眼 → L2 实时 → L3 控制），全部收在 M4 内并后置；与任务通道**进程隔离**；编码改 H.264（实测 MJPEG 13.3Mbps 不可用） | 远程桌面带宽/安全/复杂度都高，不应拖累核心任务链路 |

**需要用户拍板的事（详见第 7 章）**：原有 5 项（部署形态、iOS 交付、远程桌面范围、APK 侧载、云资源由谁提供）+ 审核后新增 4 项（实时输出口径、验收第 14 项是否纳入 1.0、审批通知/时效、离线指令语义）。其中"实时输出"与"验收第 14 项"会直接影响你对产品效果的预期与排期，建议优先确认。

## 1. 产品构思

### 1.1 一句话定位与用户画像

> **DeepSeek Remote AI = 让你离开电脑后，仍能指挥电脑上的 DeepSeek Harness 继续干活。**
> 手机是遥控器，电脑是工作台，Harness 是那个不知疲倦的程序员。

**目标用户（按优先级）**

| 优先级 | 画像 | 场景 | 关键诉求 |
|---|---|---|---|
| P0 | 独立开发者 / 一人公司 | 通勤、躺床上、出差、带娃 | "让它把重构跑完，我到了看结果" |
| P1 | 小型技术团队（2–10 人） | 领导/同事临时需要看进度、批准高风险改动 | "不在工位也能拍板" |
| P2 | AI 重度用户 / 学生 | 跑长任务、扫项目、批量整理 | "不用一直盯着屏幕" |

**核心场景（能力，不是功能列表）**

1. **离开即启动**：出门前在手机上发一句"把 auth 模块的测试补齐，跑通再提交"，电脑端 Harness 开始干活，手机随时看进度。
2. **异步收结果**：地铁上手机锁屏 20 分钟，打开 App 能看到"任务已完成 + 改了哪些文件 + 失败项原因"，而不是"重新问一遍"。
3. **远程拍板**：Harness 遇到需要授权的操作（删文件、装依赖、改配置），手机收到一张**审批卡片**：风险说明 + 影响范围 + 允许/拒绝。
4. **随时叫停**：发现方向不对，手机一键停止 → 电脑端立刻取消任务并锁死远程操作，直到本机确认。
5. **应急接管**：AI 卡住了，切到"电脑控制"看屏幕、点两下（视频级远程桌面，后期能力）。

### 1.2 差异化：我们和谁不一样

| 方案 | 能力 | 缺什么 | 我们的差异 |
|---|---|---|---|
| 向日葵 / ToDesk / 微软远程桌面 | 看屏幕、点鼠标 | 只能"人肉操作"，无法结构化执行 AI 任务；带宽高、手机费电 | 我们传的是**结构化事件**（工具调用、文件变更、审批、进度），不是视频像素；远程桌面只是补充 |
| ChatGPT / 豆包 / Kimi 手机 App | 聊天、回答问题 | 碰不到你的电脑、你的项目、你的本地环境 | 我们的 AI 在**你自己的机器**上执行，拥有完整项目上下文与本地工具链 |
| Cursor / Claude Code / Codex CLI | 强 AI 编程 | 必须在电脑前；手机端几乎不可用 | 手机端是**一等公民**：任务中心、审批卡片、通知、断线续看 |
| VS Code Tunnel / Codespaces | 远程开发 | 把开发搬到云端，环境不是你的；不是 AI 任务调度 | 我们控制的是**本机真实环境**，且以"任务"为中心而非"编辑器"为中心 |

**竞争风险（要写进路线选择里）**：如果 DSH 官方未来推出远程功能，我们的护城河必须是 **手机端产品体验 + 多设备/多 Agent 兼容的适配层**，而不是绑死某个内部接口。这正是第 2.3 节 HarnessAdapter 存在的意义。

### 1.3 产品心智模型与信息架构

**心智**：不要设计成"管理后台"，要设计成"一个随时待命、能给你汇报工作的助理"。
策划案 8 章已明确"首页突出 AI 对话"，我补充一条同样重要的原则：

> **对话是入口，任务是实体，通知是回流。**

意思是：用户天然从"说话"开始；但真正需要追踪、复看、取消、审批的是一个**任务实体**；而用户离开 App 后，靠**推送通知**把他拉回来。三者必须打通（同一份数据，三种视图），否则就会退化成"聊天记录 + 任务列表"两套割裂系统。

**五个 Tab 的信息架构构思**

| Tab | 用户带着什么问题来 | 首屏必须回答 | 关键动作 |
|---|---|---|---|
| **AI 助手**（默认首页） | "我电脑在吗？能干活吗？" | 设备连接状态（在线/离线/连接中）、当前关联会话与项目、最近一次任务摘要 | 输入/语音、上传附件、发送、停止生成、切换设备/项目 |
| **任务中心** | "交给它的活进展如何？" | 按状态分组的任务流（执行中置顶 + 进度条 + 最新一行日志） | 看详情、追加要求、取消、查看结果/变更文件 |
| **电脑控制** | "电脑现在什么状态？能看屏幕吗？" | 设备在线、Harness 状态、Agent 版本、当前活动项目、屏幕预览缩略图 | 全屏查看、缩放/横屏、申请控制授权、断开、紧急停止 |
| **项目管理** | "它能碰我哪些项目？项目里有什么？" | 授权项目列表（路径/类型/最后更新时间/Git 状态） | 浏览文件、预览、上传/下载、切换默认项目、撤销授权 |
| **个人中心** | "我的设备、安全、通知怎么管？" | 用户信息、已配对设备、安全等级 | 设备管理/撤销、通知、主题（深/浅色）、语言、关于、退出 |

**首页信息层级（AI 助手）——自上而下 3 层**

1. **状态层（小）**：`● 已连接 · USER-DESKTOP · Harness 2.x · 项目：deepseek手机端` —— 一行说清"能不能干活"。
2. **内容层（大）**：对话流（Markdown、代码高亮、可复制、工具调用折叠卡片）。
3. **输入层（固定底部）**：输入框 + 上传 + 语音 + 发送/停止切换；上方一行提示"发送给 Harness 执行，非普通问答"。

**必须显式设计的 5 个状态**（策划案 8 章要求，我给每个状态定义"用户看到什么/能做什么"）：

| 状态 | 视觉 | 文案 | 可执行动作 |
|---|---|---|---|
| 连接中 | 黄色呼吸点 | 正在连接电脑… | 取消连接 |
| 离线 | 灰点 + 设备卡片置灰 | 电脑离线，最后在线 12:31 | 重连、查看历史结果 |
| 等待授权 | 橙色高亮卡片 | 电脑端请求授权，是否允许本次操作？ | 允许/拒绝/查看详情 |
| 执行中 | 蓝色进度 + 实时日志尾行 | 正在执行（工具：RunTests） | 查看详情、追加要求、停止 |
| 失败 | 红色卡片 + 错误码 | 执行失败：退出码 1（附最后 20 行日志） | 重试、查看完整日志、复制错误 |

### 1.4 核心用户旅程（三个故事）

**故事 A：通勤执行闭环（最重要，MVP 全部验收点都在这条链上）**
> 18:30 关电脑前，手机发："把 user 模块的单测补齐并跑通，失败就修。" → App 显示"任务已创建，等待电脑执行" → 电脑 3 秒内收到 WSS 任务 → Remote Agent 新建一个 ACP 会话（`dsh --profile acp` 子进程 + `session/new{cwd}`）→ 手机看到工具调用卡片逐个出现 → 用户把手机锁屏进地铁（**关键：此时连接断开、事件继续在云端沉淀**）→ 19:05 打开 App，自动从 `lastSeq` 补偿拉取，看到"已追赶至最新：12 个文件修改，测试 48/48 通过" → 一键下载补丁或查看 diff。

**故事 B：远程审批（差异化体验）**
> Agent 收到"删除 build 目录下所有旧产物"的需求 → Harness 触发授权请求 → Agent 把审批事件上报云端 → 手机锁屏推送弹出**审批卡片**：`风险等级：高 / 影响：删除 37 个文件 / 可撤销：否` → 用户点"允许" → 任务继续。用户拒绝 → Agent 取消并回报"已按您的要求取消"。
> （若 Harness 该版本不支持审批回调，则降级为：Agent 在本地 UI 弹窗等待 + 手机端仅能"取消任务"，并在产品上**明确告知限制**——绝不伪造。）

**故事 C：紧急停止**
> 手机发现 AI 在做危险操作 → 点红色"停止" → ① 云端立即向该设备下发 `emergency.stop`；② Agent 收到后：杀子进程 → 撤销桌面输入控制 → 关闭文件写入通道 → 进入 **Locked 状态**；③ 手机端显示"已停止，电脑端已锁定，需在本机点击确认才能恢复远程控制"；④ 全程写审计日志。**电脑端始终拥有最终否决权**，这是安全设计的基石。

### 1.5 明确非目标（避免范围爆炸）

- ❌ 不做充值与支付（策划案 1.0 已定），**也不做会员/计费**——定位为免费自托管工具。
- ❌ 不把 Harness 管理接口暴露到公网，**不做**"手机直连电脑"（NAT 打洞除外，见 D3）。
- ❌ 不做多租户 SaaS、不做团队协作/共享任务（v1 个人单用户）。
- ❌ 不重写 AI Agent、不自己接模型 API（一律走 Harness）。
- ❌ v1 不做 iOS 上架 App Store（先 APK 侧载 + iOS 源码构建说明，见 7.2）。
- ❌ 不做语音唤醒/长期后台监听（隐私与耗电）。

### 1.6 成本与商业模式构思

| 项目 | 成本 | 说明 |
|---|---|---|
| 云服务器 | ¥60–120/月（2C4G，1M 带宽起） | 仅做路由/鉴权/持久化，压力很小；也可先用用户自己的服务器 |
| 域名 + TLS | ¥60/年 + 免费证书 | **必需**：手机端访问必须 HTTPS/WSS；纯 IP 也可用自签但体验差 |
| 开发者账号 | ¥0（v1 侧载）/ Google Play $25 / Apple $99/年 | v1 建议不进场商店 |
| 电脑端签名证书 | ¥0 起（自签）/ 代码签名 ¥1k+/年 | 无签名会触发 SmartScreen 警告，v1 可接受并附说明 |
| 模型成本 | 0（用户自己的 Harness 账号） | 除非未来做代理转发 |

**结论**：这是一个**零边际成本、自托管**的工具型产品，商业价值在于"让你已有的电脑算力不被闲置"，而不是卖云服务。

## 2. 技术构思

### 2.1 总体架构

![系统架构图](architecture.png)

**四条关键边界（这张图的灵魂）**

1. **电脑端永远出站**：Remote Agent 主动用 WSS 连云端，不开入站端口 → 家庭宽带/NAT 后也能用，无需公网 IP，也天然抗扫描。
2. **手机永不直连电脑**：所有流量经云端路由，便于鉴权、审计、设备撤销立即生效。
3. **Harness 永远不被公网暴露**：它只监听 `127.0.0.1`（实测），Agent 通过"子进程 CLI + 本地接口"与它通信。
4. **远程桌面通道独立**：与任务通道分进程、分权限、可单独禁用（策划案 4.3 要求）。

**组件职责表**

| 组件 | 技术 | 职责 | 不做什么 |
|---|---|---|---|
| 手机 App | Flutter | 五页 UI、对话流、任务中心、设备/项目/文件、远程桌面画面、通知 | 不直连电脑、不存模型密钥 |

### 2.2 关键设计决策（ADR 摘要）

> 详细论证与替代方案见 `docs/design/` 各分册。以下 8 条决定了整个项目的形状。

**D1 · Remote Agent 用 Node.js + TypeScript（而不是 Java / C# / Python）**
- **理由**：要与 DSH 的子进程 CLI、Cordis 插件（TS）打交道，同生态可以直接复用类型定义、进程管理、事件解析；无 JRE 运行时依赖（对比 Java 需 ~200MB 运行时）；打包体积小（Electron 壳可复用 Tauri 或直接 Node + 托盘）；与云端 Java 的分工也清晰（云端管数据，电脑端管执行）。
- **代价**：与后端语言不统一，需维护两套构建；用 OpenAPI 生成 TS 客户端把契约固化来抵消。
- **否决项**：Java Agent（重、启动慢、跨进程调用 CLI 笨重）；Python（Windows 打包与签名体验差）。

**D2 · 接入 Harness：ACP 子进程为主通道 → 官方插件桥做增强 → 桌面自动化不采用**
- **实测结论**：官方 `dsh --profile acp` 随 DSH 分发（shipped profile），走 **ACP（Agent Client Protocol）**，NDJSON JSON-RPC 2.0 over stdio；对话 / 步骤级流式事件 / 工具调用 / 取消 / 审批 / 跨进程 resume / 模型与推理强度切换，全部实测闭环。`dsh headless` 虽有 `--json` 结构化输出，但**无审批通道、无取消**，只适合一次性批任务。
- **分层**：L1 ACP 子进程（主通道，`connect/sendMessage/getEvents/cancel/approve/setModel`）；L2 官方 Cordis 插件桥（**仅当**需要附着用户正在运行的桌面实例的 live 会话，或需要 token 级流式时才启用）；L3 桌面 UI 自动化（模拟键鼠）**不采用**——违反策划案 3.2 的"不得绕过权限"，且版本升级即失效。
- **原则**：适配层把"能力不可用"变成**结构化错误**（`CAPABILITY_UNAVAILABLE`），绝不用模拟数据冒充真实执行（策划案反复强调的底线）。
- **已知边界**：ACP 客户端侧**没有文件读写方法**（`fs/*` 由 Agent 内部工具完成，工作目录由 `session/new{cwd}` 固定）→ 文件能力必须由 Remote Agent 本地实现并受项目授权目录约束，正好落在策划案 3.3 的 `readFile/writeFile`。

**D3 · 云端只做"路由 + 鉴权 + 持久化 + 审计"，不做任务编排**
- **理由**：任务状态的真实来源是电脑端 Harness；云端若做编排会变成"双写状态源"，断线后必然不一致。云端保存的是**事件流**（append-only），可重放、可审计、可补偿。
- **代价**：云端无法在电脑离线时代为执行（这正是我们要的——诚实告诉用户"电脑离线"）。

**D4 · 通信形态只有一种（云中继），但"云端部署在哪"可配置**
- **定案（审核 P0-1 收敛）**：手机 → 云端 → Agent 的**中继形态唯一**；手机永不直连电脑、Agent 永远出站（这是安全边界，也是 62492 不可依赖的直接推论）。不做 `DirectTransport`，避免"直连/中继"两套鉴权模型与验收分歧。
- **实现**：Agent 内部 `Transport` 接口（`connect/send/onMessage/close`）+ 单一 `WssRelayTransport`，**服务端地址可配置**。早期把 Java 后端跑在自己 PC/NAS（Docker Compose，1 天），手机经 Tailscale/WireGuard 访问这个后端；后期只把后端迁到公有云，Agent 改一个 URL，**协议与代码零改动**。
- **代价**：早期需要手机装一次 Tailscale（或用局域网）；换来的是零服务器采购即可验证产品，且不引入第二套安全模型。

**D5 · 事件流模型：可追赶的日志（cursor-based），不是"实时流"**
- **理由**：手机锁屏/切后台/换网络是常态，实时流必然断。设计成"带 seq 的 append-only 事件日志 + 客户端 lastSeq 补偿"，断线重连后自动追赶；实时只是"追赶的一种特殊情况"。
- **实现**：每个 task 的事件 `seq` 单调递增；客户端保存 `lastSeq`；重连时 `resume(taskId, lastSeq)` 返回缺失区间；超过保留窗口则返回"历史已归档 + 最终快照"。
- **这是本项目在技术上的**核心创新点**，也是与"普通 WebSocket 聊天"最大的区别。详见 2.4。

**D6 · 远程桌面独立进程 + 分级授权 + 后置**
- **理由**：屏幕采集/编码/传输/输入注入是另一套安全模型，混入主进程会让核心链路变脆。
- **分级**：查看（一级授权）→ 控制（五级授权，逐次确认）→ 高风险（六级，额外确认）。
- **路线**：收在 M4 内，分三级——L1 看一眼（H.264 推流，2–3Mbps，2 人日）→ L2 WebRTC 实时（P1，5–8 人日，可砍）→ L3 输入控制（P2，3–4 人日，逐次授权）。

**D7 · 数据模型对齐"会话 = Harness 会话"，任务 = 事件聚合视图**
- **理由**：策划案表 2 的 `conversations/messages/tasks` 容易设计成聊天 app 模型；实际上 Harness 的会话才是真源，本项目的会话表只是**映射与索引**（`harness_session_id` 是外键世界的锚点）。任务不是"消息"，而是"一次投递 + 事件流聚合出的状态机"。
- **好处**：手机端"对话视图"与"任务视图"读同一份数据，不会出现"聊天里说完成了、任务中心显示失败"的割裂。

**D8 · 发布形态：Android APK 侧载优先，iOS 源码 + 构建说明**
- **理由**：上架审核周期、政策风险、iOS 需 macOS 构建；v1 目标是"自己/愿意折腾的人能用"。
- **代价**：分发体验差 → 用清晰的安装文档 + 应用内检查更新缓解。

### 2.3 接入层构思：HarnessAdapter（项目成败的关键抽象）

策划案 3.3 已经给出了抽象接口。基于实测，我的构思是**把它做成"一层主通道 + 一层可选增强 + 一张实测能力矩阵 + 统一降级语义"**：

```
┌─────────────────────────────────────────────────────────────┐
│                  HarnessAdapter (TypeScript 接口)            │
│  connect / getStatus / sessions / sendMessage / getEvents /  │
│  cancel / approve / setModel / workspaces / readFile / ...   │
└────────────────┬───────────────────────────┬────────────────┘
                 │                           │
  ┌──────────────▼──────────────┐  ┌─────────▼─────────────────┐
  │ L1 主通道：ACP 子进程         │  │ L2 增强（可选）：官方插件桥 │
  │ dsh --profile acp            │  │ Cordis 插件 + 本地 WS      │
  │ NDJSON JSON-RPC 2.0 / stdio  │  │ 附着桌面 live 会话、        │
  │ 对话·步骤级流式·工具调用·     │  │ token 级流式；默认不启用    │
  │ 取消·审批·resume·模型切换     │  │                            │
  └──────────────┬──────────────┘  └─────────┬─────────────────┘
                 │                           │
  ┌──────────────▼───────────────────────────▼─────────────────┐
  │ L0 本地能力层（Remote Agent 自己实现，不经过 DSH）             │
  │ 文件/工作区/终端/文件传输/Git 状态 —— 受项目授权与六级权限约束  │
  │ （ACP 没有文件读写方法，这一层是必需的，不是兜底）             │
  └─────────────────────────────────────────────────────────────┘
```

**能力矩阵（全部来自实测，逐条标注"测到了没有 / 不支持怎么办"）**

| 能力（策划案 3.3） | 实现方式 | 实测状态 | 不可用时的降级 / 用户可见行为 |
|---|---|---|---|
| `connect()/disconnect()` | 启动 `dsh --profile acp` 子进程 → `initialize`（返回 `protocolVersion: 1`） | ✅ 实测 | 起不来 → `HARNESS_OFFLINE`，状态点灰、禁止发送 |
| `getStatus()` | initialize 结果 + 进程/版本探测 + 当前会话 | ✅ 实测 | 显示版本与模型；未知时明确写"未知"，不猜 |
| `getSessions()/createSession()` | `session/list`（跨进程列出持久化会话）、`session/new{cwd}`、`session/resume`、`session/close` | ✅ 实测（sessionId 为裸 UUID） | 无历史会话 → 空态 + "新任务=新会话" |
| `sendMessage()/getSessionEvents()` | `session/prompt` → `agent_message_chunk` / `agent_thought_chunk` / `tool_call`（含 rawInput 完整命令）/ `tool_call_update` / `usage_update` | ✅ 实测；**提交点粒度**（非 token 级） | UI 如实呈现"步骤级实时 + 提交点消息"，不做假的 token 打字机 |
| `cancelTask()` | `session/cancel` 通知 → `stopReason: cancelled` | ✅ 实测，**取消后会话仍可继续** | "已取消，可继续对话"（覆盖策划案 2.3 的取消要求） |
| `continueTask()` / 中断续跑 | 同一 sessionId 再发 prompt；跨进程用 `session/resume` 恢复上下文 | ✅ 实测 | 中断后可续，不必重开会话 |
| **审批（waiting_approval）** | `session/request_permission`：allow-once → 工具执行；reject-once → 工具 failed、Agent 解释原因、turn 正常结束 | ✅ **完整闭环实测** | 手机弹审批卡片（允许/拒绝），见故事 B；默认超时=拒绝 |
| 暂停/继续（中途暂停） | ACP 无"暂停"原语，只有 cancel + 续跑 | ❌ 不支持 | **明确显示"当前版本不支持暂停"**（策划案 2.3 要求），提供"取消/继续"两个动作 |
| 模型 / 推理强度切换 | `session/set_config_option`（model 分组、`reasoning_effort`: off/low/high/max） | ✅ 实测 | 手机设置页可选；失败回退默认值并提示 |
| `getWorkspaces()/getWorkspaceFiles()/readFile()/writeFile()` | **L0 本地实现**（ACP 无文件方法） | ⏳ 待实现 | 仅授权目录可见；写操作走六级权限 + 审批 |
| 并发 | 单 ACP 进程多 session，跨 session 并行；同 session 第二个 prompt 返回 `-32602 a prompt is already in flight` | ✅ 实测 | 同一会话串行入队；执行并发与云端准入见下方"并发口径" |

**并发口径（统一，审核 P2-2）**：三个数字不是同一个东西，分开定义免得打架——
- **Agent 执行并发**：默认 **2**（可配 1–5），即同时最多几个 ACP session 在跑（`REMOTE_AGENT.md §5.2`）；第 3 个任务排队并回传 `task.queued`。
- **同一会话**：prompt 严格串行，第二个 prompt 直接 `SESSION_BUSY`（-32602），手机端显示"当前对话正在执行，可排队"。
- **云端准入**：单设备在途任务上限 10（`PROTOCOL.md §1.9`），超出返回 `429`，防脚本刷任务。

**降级语义（统一错误码）**：`CAPABILITY_UNAVAILABLE` / `HARNESS_OFFLINE` / `ACP_PROTOCOL_ERROR`（rc 契约变更或未识别事件）/ `SESSION_BUSY`（-32602）/ `PERMISSION_DENIED` / `TASK_TIMEOUT` / `APPROVAL_REJECTED` / `VERSION_UNSUPPORTED`。
→ 手机端永远能区分"没做"和"做不到"，这是产品可信度的来源，也是策划案"不得伪造"要求的技术落地。

### 2.4 核心创新点：把"实时流"设计成"可追赶的事件日志"

**问题**：普通远程控制软件假设你在看屏幕；手机用户 90% 时间不在看。如果按"实时流"设计，锁屏 20 分钟回来就丢了一段过程，用户只能看到最终结果——出错了根本不知道哪一步错的。

**构思**：每个任务是一条 **append-only 事件流**，手机端是"订阅 + 追赶"的读者。

```
Agent:  task-42: evt#1 task.started
                  evt#2 tool_call RunTests      ← ACP tool_call（rawInput 含完整命令）
                  evt#3 tool_result exit=1      ← ACP tool_call_update
                  evt#4 task.output "...修复第 3 个断言..."  ← ACP 提交点消息（非 token 级）
                  evt#5 task.completed
云端:   持久化 event(seq, task_id, type, payload, ts)
手机:   在线 → 实时推送；断线 → 重连后 resume(taskId, lastSeq=2) → 补发 3,4,5
        UI 显示"已从 12:31 追赶至最新（3 条）"
```

**配套细节（看起来小，决定成败）**

- **seq 单调递增 + 服务端保留窗口**：默认保留 7 天/每任务 5 万条，超出后归档为"最终快照 + 摘要"。
- **msgId + 幂等**：客户端重发同一 msgId，服务端只处理一次（任务不重复执行）。
- **事件合并**：`task.output` 以 **2 秒 / 4KB** 窗口合并后推送（ACP 是提交点粒度，本身不是 token 流），手机端省电省流量。
- **心跳 25s + 指数退避重连**（1s→2s→4s…上限 30s），移动端切换网络时快速自愈。
- **"追赶到最新"是一个明确的 UI 状态**，而不是无限滚动加载。

### 2.5 协议摘要（细化见 `docs/design/PROTOCOL.md`）

**统一消息信封**（REST 与 WSS 共用）：

```json
{
  "v": 1,
  "msgId": "01J8Z9K3M4N5P6Q7R8S9T0",
  "type": "task.output",
  "ts": 1761922800123,
  "deviceId": "dev_7f3a",
  "taskId": "tsk_91c2",
  "conversationId": "cnv_5b8e",
  "seq": 37,
  "payload": { "stream": "stdout", "text": "Running tests...", "level": "info" }

```

> 以分册为准（审核 P1-5）：信封字段是 `conversationId`（对话）/`taskId`（任务）/`deviceId`（设备）三层，均带 `v` 与 `seq`；`conversationId` 与 Harness 的 `sessionId` 一一映射（映射关系存 `conversations.harness_session_id`）。

**事件类型**：策划案 6.1 的 **13 个标准事件全部对齐、无增删**（`device.online/offline`、`task.created/started/progress/output`、`task.waiting_approval/completed/failed/cancelled`、`session.message`、`desktop.connected/disconnected`）；另定义 **8 个扩展事件**（审批请求/审批结果、急停、审计、设备配对、Agent 心跳、任务排队等），类型名以 `PROTOCOL.md §6.13` 为唯一真源，本文不另行枚举（避免再次出现"摘要与分册不一致"）。

**REST**：策划案表 3 的 17 个接口全部保留、逐条对应（`PROTOCOL.md` 表 3）；另补 **11 个实现必需端点**：`auth/refresh`、`auth/logout`、`auth/me`、`POST/DELETE agent/pairing-sessions`、`agent/token/rotate`、`GET approvals`、`POST approvals/{id}/decide`、`tasks/stats`、`health`、`jwks`（完整签名见 `PROTOCOL.md §2.18`）。统一 `{code,message,data,traceId}` 响应、`Idempotency-Key` 支持、游标分页。

### 2.6 数据模型摘要（细化见 `docs/design/DATA_MODEL.md`）

策划案表 2 的 **8 张表全部保留**；实现上共 **8 张核心表 + 8 张支撑表**（DDL 见 `DATA_MODEL.md`，审核已核对字段计数）：

| 分类 | 表 | 作用 |
|---|---|---|
| 核心 8（策划案） | `users` `devices` `device_pairings` `conversations` `messages` `tasks` `audit_logs` `workspace_permissions` | 一一对应策划案表 2 |
| 支撑 8（实现必需） | `refresh_tokens` `idempotency_keys` `device_events` `device_commands` `files` `approvals` `desktop_sessions` `user_settings` | 刷新令牌、幂等、**按设备 seq 的事件流（断线补偿的数据源）**、云端→Agent 指令、文件、审批单、桌面会话、用户偏好 |

- **事件流不在 `tasks` 里**：`device_events(device_id, seq, type, payload jsonb, ts)` 就是 2.4 的可追赶日志，`messages` 只存用户可见的对话内容；二者通过 `task_id`/`conversation_id` 关联（不再需要臆造的 `task_events` 表）。
- **已知待补字段（审核 P1-3）**：`tasks` 缺"所属项目/工作区"外键、`workspaces` 缺 `type`（策划案 2.5-a 的"项目类型"）—— 列入 v1.0 冻结前的数据模型补齐项（0.5–1 人日）。

### 2.7 安全构思：六道闸门 + 三段式紧急停止

**信任边界**：手机（不可信网络）→ 云端（半可信，持有元数据）→ 电脑（**最终决策者**）。安全原则一句话：

> **云端可以"请求"，但只有电脑端能"决定"。**

**六道闸门**

| # | 闸门 | 机制 |
|---|---|---|
| 1 | 登录 | 密码 Argon2id 哈希；JWT access(15min) + refresh(30d)；异常登录告警 |
| 2 | 配对 | 电脑端生成二维码（含一次性配对令牌 hash，5 分钟有效、单次使用）；手机扫码后建立 device 绑定；未配对设备一律拒绝 |
| 3 | 传输 | 全链路 TLS（HTTPS + WSS）；不裸传任何凭证；日志脱敏（token/password/path 打码） |
| 4 | 权限分级 | 策划案 6 级权限落成**中间件 + Agent 二次校验**（双端校验，防止云端被绕过）：一级看状态、二级对话任务、三级项目文件、四级终端、五级桌面控制、六级高风险确认 |
| 5 | 高风险确认 | 删除/覆盖/批量修改/系统命令/安装软件 → 手机端**二次确认卡片**（默认拒绝、带倒计时）+ 审计记录；电脑端本地 UI 同步可见 |
| 6 | 撤销与停止 | 设备撤销 → 云端立即拒新指令 + 断开 WSS；紧急停止 → 三段式（见下） |

**紧急停止（三段式，电脑端永远有效）**

```
手机点停止 ──► 云端广播 emergency.stop ──► Agent 执行：
      ① 杀任务子进程（SIGTERM → 5s 后 SIGKILL）
      ② 断开桌面输入通道（只断输入，保留画面）
      ③ 进入 Locked 状态：拒绝一切远程指令，直到本机点击"解除锁定"
      └─► 全程写 audit_logs；手机端显示"已停止 + 电脑端已锁定"
```

**电脑端本地保障**（策划案 3.4 / 7.4）：托盘常驻图标显示"正在被远程控制"、本地紧急停止快捷键、开机启动必须用户主动勾选（默认关闭）。

### 2.8 远程桌面构思：先做"看一眼"，不追 WebRTC 完美

**实测前提（`docs/research/ENVIRONMENT_REPORT.md` 附录 C）**：ffmpeg gdigrab 抓屏可用；1280 宽 / 10fps 下 **MJPEG≈13.3Mbps（公网不可接受）、H.264≈3.0Mbps、NVENC≈1.76Mbps**。所以编码必须走 **H.264（NVENC 优先 → libx264 兜底），MJPEG 只作局域网/演示**——该修正已同步到设计分册（ADR-ROAD-011）。

| 层级 | 实现 | 成本 | 结论 |
|---|---|---|---|
| **L1 看一眼**（MVP 必做） | 屏幕采集（gdigrab/Graphics Capture）+ H.264 推流 2–3Mbps 约 10fps；云端只转发不落盘 | 2 人日（含在 M4） | **先做它**，满足"看一眼卡在哪" |
| L2 实时查看（P1） | WebRTC（H.264/VP8 + DataChannel）+ 弱网自适应 | 5–8 人日 | 有 L1 后再评估，可砍 |
| L3 输入控制（**验收第 14 项要求，争议项**） | 逐次授权 + 单次/限时会话；本地可随时急停 | 3–4 人日 | **二选一（见第 7 章 D-7）**：A 纳入 1.0 必做（M4 20→23–24 人日，总计 87–88 / 含 buffer 105–106）；B 书面变更需求，v1 只读屏幕、验收第 14 项改期 |

**关于 L3 的判断**：审核把这一点列为 P0-2 —— 策划案 2.4 与第十章都要求"授权后控制电脑"且"18 项逐项真实测试"，**不能既标 P2 可在验收表里保留**。我倾向 A（纳入 1.0），因为输入控制是"远程操作电脑"这个卖点的最后一块拼图，且 3–4 人日成本可控；但这条必须由你拍板，因为它直接改总工期。

**构思要点**：① 屏幕数据**端到端不外存**（云端只转发不落盘）；② 查看与控制是两次独立授权，控制授权可单次/限时；③ 桌面链路与任务链路**进程隔离**（独立子进程与端口），桌面崩了不影响任务执行；④ 若仍走截图轮询（局域网/演示），只允许 JPEG/WebP 单帧，不承诺流畅。

### 2.9 手机端技术构思（细化见 `docs/design/MOBILE_UI.md`）

- **状态管理**：Riverpod（编译期安全、易测试、社区主流）优先于 Bloc（样板代码多）。
- **目录结构**：`features/{assistant,tasks,devices,projects,profile}` + `core/{net,ws,storage,theme}`，按功能切分而不是按层切分。
- **会话缓存**：本地 SQLite（drift）缓存会话/任务/事件窗口 → 冷启动先显示缓存再增量刷新（离线也能看历史结果）。
- **通知**：任务完成/失败/待审批三类推送；若不做推送服务，退化为"前台轮询 + 打开即追赶"（M2 决策点）。
- **主题**：深/浅色两套 token（策划案 8 章要求），跟随系统。
- **大屏适配**：手机竖屏为主，平板/横屏对话 + 设备状态双栏。

## 3. 可行性评估（基于实测，非推测）

### 3.1 Harness 接入可行性（这是全项目最大的技术风险，现已基本消除）

> 本节所有结论都来自本机实测（约 25 次真实 turn、多个探测脚本），不是推测。证据与源码行号见 `docs/research/HARNESS_INTERFACES.md`。

| 能力 | 结论 | 证据 | 影响 |
|---|---|---|---|
| **ACP 服务端（官方）** | ✅ 可用，且是官方 shipped profile | `dsh --profile acp`；ACP `initialize` 返回 `protocolVersion: 1`；包 `dsh-acp` / `dsh-acp-app`、`@agentclientprotocol/sdk` 随 DSH 分发 | **主通道定案**，M0 主路线成立 |
| 对话 / 多轮 / 工具调用 / 流式 | ✅ 实测闭环 | `session/prompt` → `agent_message_chunk`、`agent_thought_chunk`、`tool_call`(rawInput)、`tool_call_update`、`usage_update` | 手机端"实时日志"精度 = **提交点级**（非 token 级），方案如实标注 |
| 取消 | ✅ 实测 | `session/cancel` → `stopReason: cancelled`，且**同会话可继续** | 任务中心"取消"可用 |
| **审批（高风险确认）** | ✅ 实测闭环 | `session/request_permission`：allow-once → 工具执行并写文件成功；reject-once → 工具 failed、Agent 解释、turn 正常 end_turn | 策划案"等待用户授权"状态可真实实现 |
| 会话管理 / 续跑 | ✅ 实测 | `session/new{cwd}`、sessionId=裸 UUID、`session/list` 跨进程列出持久化会话、`session/resume` 恢复上下文 | 历史会话、断点续跑可做；**与桌面实例 live 会话共用需 B 路线** |
| 并发 | ✅ 实测 | 单进程多 session、跨 session 并行（总耗时≈max 而非 sum）；同 session 第二个 prompt → `-32602 a prompt is already in flight` | 单设备 3 并发、同会话串行入队 |
| 模型 / 推理强度 | ✅ 实测 | `session/set_config_option`（model 分组、reasoning_effort off/low/high/max） | 手机设置页可选 |
| 文件读写（客户端侧） | ❌ ACP 无此方法 | 服务端只注册 initialize / authenticate / session-new / list / resume / close / set_config_option / prompt，通知只有 session/cancel | 文件能力由 **Remote Agent L0 本地层**实现（受授权目录约束） |
| 一次性批任务 | ✅ 但有限制 | `dsh headless --json` 固定 NDJSON 事件，**无审批通道、无取消** | 仅用于无交互批任务，不作主链路 |
| 本地 HTTP（62492） | ✅ 存在但不可依赖 | 官方 Web 前端内部 RPC：launch-token→cookie、Host 栅栏、仅 loopback、随机端口、无文档 | 不作接入方案 |
| 插件桥（B 路线） | ✅ 可用，作增强 | Host 79 个 Event、`webServer.register/registerUpgrade`；dsh-pocket（GPL-2.0，已装被禁用）已验证"反代 + WS 全透传"可行 | 仅当必须附着桌面 live 会话或要 token 级流式时启用 |

**风险修正**：原以为最大风险是"能否驱动真实 Harness"，实测后已消除；当前唯一实质风险变为 **ACP 仍是 rc 版本（0.2.1-rc.5）且无随包公开文档**。对策已写入 D2 与 R2：锁版本、忽略未知 `session/update` 类型、JSON-RPC 错误统一映射、每次升级跑回归探测脚本（`tools/harness_probe/`）。

### 3.4 结论

**技术可行性：高（已从"待验证"变为"已验证"）**。ACP 主通道、审批闭环、取消、续跑、并发、模型切换全部本机实测通过；剩余风险只有 rc 版本契约漂移（可控）。
**工程可行性：中高**。总工作量经设计分册细化后为 **84 人日**（不含缓冲；按 20% 缓冲为 **101 人日**），明细见第 4 章与 `docs/design/MVP_AND_ROADMAP.md` §9。该数字**未计入**：项目初始化 1 人日、iOS 构建、云资源采购与上线运维；若 D-7 采纳"L3 输入控制纳入 1.0"再加 3–4 人日 → **87–88（含缓冲 105–106）**，实际成本区间 **88–105 人日**。M0 已因本次调研从"验证"压缩为"固化"（3 人日）。AI 辅助开发可压缩日历时间，但联调与远程桌面不可压缩。
**资源可行性：中**。环境基本齐备（JDK/Android/Node/打包链都在），需补 Flutter（P0，约 0.5–1 天）与 PostgreSQL；云服务器/域名可先推迟（后端先自托管在自己 PC/NAS，手机经 Tailscale/WireGuard 接入这个"云端"）。
**最大非技术风险**：需求范围膨胀（策划案覆盖 5 个端 + 远程桌面），必须严格执行"里程碑优先级 + 非目标清单"。

## 4. 实施构思：M0–M5（风险优先，与策划案八阶段对齐）

### 8.3 审批终态权威表（建议；P0-3 的收敛方案）

原则一句话：**"用户拒绝/超时"不是系统失败，只有"请求本身无法完成"才是 failed。** 手机端绝不能把用户的"不允许"显示成红色的"执行失败"。

| 场景 | 任务终态 | `errorCode` | 手机端显示 | 备注 |
|---|---|---|---|---|
| in-flight 审批：允许（allow_once） | `completed`（执行结果照常回传） | 无 | 继续 | ACP 工具已执行 |
| in-flight 审批：拒绝（reject_once） | `completed` | 无（`result.note=user_rejected`） | "你拒绝了该操作，AI 已说明后续" | Agent 停止该工具、解释原因、turn 正常结束（实测） |
| in-flight 审批：超时（D-8 的 10 分钟） | `completed` | 无（`result.note=approval_timeout`） | "审批超时，已按拒绝处理" | 同拒绝路径，留痕可审计 |
| pre-flight 确认（高风险/新增授权目录）：拒绝 | `failed` | `70003 APPROVAL_REJECTED` | "你拒绝了高风险操作" | 操作未进入执行 |
| pre-flight 确认：超时 | `failed` | `70004 APPROVAL_TIMEOUT` | "确认超时，未执行" | 与 70003 区分，便于统计 |
| 审批票据/设备凭证校验失败 | `failed` | `50002 AUTH_INVALID` | "授权凭证无效，请重新授权" | 安全事件，写审计 |

## 9. M0 执行结果（2026-10-31）与下一步

第 8.4 节之后的建议指令是"M0：把 ACP 接入封装进 `agent/`"。**该指令已被执行并验收通过**，这里只记结论，细节见独立报告 [`docs/research/M0_FEASIBILITY.md`](../research/M0_FEASIBILITY.md)。

| 验证层 | 结果 | 证据 |
|---|---|---|
| 单元测试（不依赖 Harness） | **36/36 通过** | `agent/tests/unit/` |
| 合同测试（真实 Harness 0.2.1-rc.5） | **9/9 通过**（28.3s）：initialize、能力矩阵、session、真实 turn、多轮、取消、审批 allow、审批 deny、resume | `agent/evidence/contract-2026-10-31T04-27-46-505Z.jsonl` |
| 端到端冒烟 | **5/5 通过**（20s）：连接 → 真执行建文件 → 审批写入 → 执行中取消 → 断线续跑 | `agent/evidence/e2e-2026-10-31T04-28-48-670Z.json` |

**M0 结论对本构思的三处修正**：
1. **D-6（实时口径）应定"步骤级实时"**：ACP 事件是提交点粒度，token 级流式不存在，写进验收口径比含糊承诺更负责。
2. **D-8（审批通知）不是优化项**：实测审批等待可达数分钟，手机锁屏/后台收不到通知会直接卡死任务，建议直接采纳"前台服务 + 本地通知"。
3. **工作区权限要进安装引导**：Windows 工作区若缺 `WRITE_OWNER`，Harness shell 工具会报 `SetNamedSecurityInfoW failed (Win32 5)` 且仅表现为"命令跑不了"；修复方式已固化为 `agent/scripts/ensure-workspace-acl.ps1`，生产安装器应内置。

M1 的第一行代码仍然不变：`RemoteAgent` 的 `Transport` 接口 + `AcpHarnessAdapter`（后者已在 M0 完成，M1 直接复用）——因为这两者决定了整个系统能不能被验证。M1 任务分解与验收标准见 M0 报告 §8。
